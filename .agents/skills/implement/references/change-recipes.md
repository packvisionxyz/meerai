# Change recipes by layer

Use the profile §5 to find the canonical implementation in the repo. These are the questions that
apply in any codebase.

## Transport

- Where is the route/RPC/command registered? Add the new unit there, not in a side file.
- What validates the input, and what type does it validate into?
- Where does identity/tenant come from? It must come from the session or the verified token, never the
  request body.
- Which guard/middleware runs before the handler? Pick the narrowest that fits.
- Does the handler only translate, or does it hold rules? Rules belong in the domain layer.
- How are errors mapped? Match the existing code, not a new scheme.
- What tests cover auth extraction and error mapping?

## Domain

- Where do rules live today? Keep them out of transport.
- Who owns each state transition? One place should.
- Does a read-check-then-write span more than one query? It needs a transaction.
- Can the operation run twice safely? Make it idempotent or guard it.
- Does it touch another domain's data directly? Use that domain's service/API instead.
- Are limits, quotas, or entitlements enforced here or at the boundary? Keep one enforcement point.
- What happens on partial failure? Define the compensating action.

## Persistence

- Is this a schema change? Add a new numbered migration pair; never edit a committed one.
- Is the schema snapshot / generated client refreshed before compilation needs it?
- Are queries parameterized and column-qualified?
- Are writes scoped to the tenant/organization in the `WHERE` clause, not only in Go/TS?
- Is the read one round-trip where it matters? Prefer a join/CTE over sequential queries.
- Are timestamps `timestamptz` (or the repo's equivalent) and generated by the database?
- Are indexes added for the access path you introduced?
- Is there a backfill? Is it safe to run twice? Is it reversible?

## Background

- What starts the work, and what stops it? Every loop must observe cancellation.
- Is the queue bounded, and what happens under backpressure? Drop oldest, block, or reject — pick one
  deliberately.
- Are retries bounded and idempotent? Where is the dead-letter path?
- Does it spawn a child process? Graceful stop, reap, and keep the exit status readable.
- Is blocking work off the event loop / async runtime?
- What log or metric proves it is alive and correct?
- Does shutdown drain in-flight work before closing handles?

## Client data

- Is every read defined once (query/cache module), with a stable key?
- Do mutations invalidate the keys they affect?
- Do route loaders prefetch through the same definition, not a duplicate call?
- Are loading, empty, error, and stale states handled explicitly?
- Do optimistic updates roll back on failure?
- Is server state kept out of global stores?

## UI

- Does a shared primitive already exist? Extend by composition before copying.
- Are colors, spacing, and typography from design tokens, not literals?
- Is every user-facing string localized in all supported locales?
- Does every input have a label, and every icon button an accessible name?
- Are stable test hooks present on interactive elements and status states?
- Does the layout hold at the repo's supported breakpoints?
- Does every effect that opens a subscription, socket, track, or interval return cleanup?

## Configuration

- Is the variable declared everywhere it is read (schema, example file, deployment, CI)?
- Does a missing required value fail loudly at startup?
- Is the default safe for production?
- Are secrets absent from source, logs, and error messages?
- Do all environments agree on the name and shape?
